  ## 2. Model-by-Model Specifications                                                                                                                                               
                                                                                                                                                                                    
  ### 1. RoBERTa (Sentiment Analysis)                                                                                                                                               
                                                                                                                                                                                    
  1. Selection Rationale: Better performance than standard BERT due to dynamic masking and removal of next-sentence prediction. Ideal balance of contextual performance and sequence
  classifier inference speed.                                                                                                                                                       
  2. Input Data:  clean_review_text  (truncated to 512 tokens).                                                                                                                     
  3. Output Data: Probability scores for positive, negative, and neutral, along with the predicted class label and a confidence score.                                              
  4. Training Strategy: Supervised transfer learning. Finetune a pre-trained  roberta-base  classification head on the Amazon Reviews dataset.                                      
  5. Fine-tuning Requirements: Set up standard cross-entropy loss, Hugging Face  Trainer  API, learning rate of 2e-5, weight decay of 0.01, and AdamW optimizer. Split: 80% train,  
  10% validation, 10% test.                                                                                                                                                         
  6. Inference Workflow: Tokenize input text → Send input to Triton (PyTorch backend) → Execute forward pass → Apply Softmax to model logits → Map outputs to DB.                   
  7. Expected Latency: ~15ms on an NVIDIA T4 GPU (real-time batch size 1); ~3ms per review with dynamic batching (batch size 64).                                                   
  8. Hardware Requirements: NVIDIA T4, L4, or A10G GPU for training and hosting.                                                                                                    
  9. Storage Requirements: ~500 MB for model weights.                                                                                                                               
  10. Scalability: Compile to TensorRT to reduce footprint and improve latency.                                                                                                     
                                                                                                                                                                                    
  ### 2. spaCy Transformer (NER)                                                                                                                                                    
                                                                                                                                                                                    
  1. Selection Rationale: spaCy's  en_core_web_trf  (built on RoBERTa-base) provides production-grade speed and reliability. It parses text accurately, making it suitable for      
  extracting Brands, Products, Organizations, and Locations from review contexts.                                                                                                   
  2. Input Data:  clean_review_text .                                                                                                                                               
  3. Output Data: A list of structured entity records: entity text, label (BRAND, PRODUCT, ORG, LOC, FEATURE), starting index, and ending index.                                    
  4. Training Strategy: Transfer learning and entity definition tuning. Annotate reviews using tools like Prodigy (e.g., labeling specific features like "battery life" or "screen").
  5. Fine-tuning Requirements: Adapt spaCy config templates for  spacy-transformers  to train the NER head while freezing the transformer backbone weights to avoid catastrophic    
  forgetting.                                                                                                                                                                       
  6. Inference Workflow: Input text → Run spaCy pipeline tokenizer → Forward pass through RoBERTa backbone → Predict boundaries via transition-based parser.                        
  7. Expected Latency: ~45ms per review on a GPU.                                                                                                                                   
  8. Hardware Requirements: Minimum 8GB VRAM GPU (Inference) and 16GB VRAM (Training).                                                                                              
  9. Storage Requirements: ~400 MB.                                                                                                                                                 
  10. Scalability: Execute batch runs via  nlp.pipe()  inside asynchronous Celery tasks to prevent bottlenecking the main process.                                                  
                                                                                                                                                                                    
  ### 3. all-MiniLM-L6-v2 (Embeddings)                                                                                                                                              
                                                                                                                                                                                    
  1. Selection Rationale: MiniLM is extremely lightweight (22M parameters) and maps sentences to a dense 384-dimensional vector space. It is faster and smaller than  all-mpnet-    
  base-v2  while retaining over 90% of its performance.                                                                                                                             
  2. Input Data:  clean_review_text  (truncated to 256 tokens).                                                                                                                     
  3. Output Data: A 384-dimensional floating-point vector.                                                                                                                          
  4. Training Strategy: Typically used out-of-the-box (zero-shot transfer) as it is pre-trained on over 1B sentence pairs. For domain-specific alignments, use Contrastive Learning.
  5. Fine-tuning Requirements: Fine-tune using the  SentenceTransformers  library with a  MultipleNegativesRankingLoss  objective if specialized search alignments are needed.      
  6. Inference Workflow: Raw text → Sentencepiece Tokenizer → Encoder → Mean pooling of token embeddings → Unit normalization.                                                      
  7. Expected Latency: <5ms on CPU; <1ms on GPU.                                                                                                                                    
  8. Hardware Requirements: Low resources. Standard CPU instance is sufficient.                                                                                                     
  9. Storage Requirements: ~90 MB for weights.                                                                                                                                      
  10. Scalability: Highly scalable. Can be deployed on standard x86 CPU Kubernetes clusters without GPU limits.                                                                     
                                                                                                                                                                                    
  ### 4. DeBERTa ABSA (Aspect Based Sentiment Analysis)                                                                                                                             
                                                                                                                                                                                    
  1. Selection Rationale: DeBERTa-v3 uses a disentangled attention mechanism and relative positions, outperforming RoBERTa on text classification. ABSA requires analyzing the      
  specific sentiment surrounding an aspect (e.g., "the battery is bad but the display is great").                                                                                   
  2. Input Data:  clean_review_text  paired with an aspect candidate (e.g.,  [CLS] Battery [SEP] The battery is bad... [SEP] ).                                                     
  3. Output Data: Sentiment label (positive, negative, neutral) and confidence score for each aspect.                                                                               
  4. Training Strategy: Supervised training on ABSA datasets (e.g., SemEval reviews) mapped to product domains.                                                                     
  5. Fine-tuning Requirements: Cross-entropy classification loss using a token-classification head over the span of identified aspect terms.                                        
  6. Inference Workflow: Extract aspects → Construct Text-Aspect pairs → Tokenize → Run DeBERTa classifier → Output aspect-sentiment mapping.                                       
  7. Expected Latency: ~60ms to 90ms per review depending on the number of aspects processed.                                                                                       
  8. Hardware Requirements: A10G or L4 GPU recommended.                                                                                                                             
  9. Storage Requirements: ~800 MB for model weights.                                                                                                                               
  10. Scalability: Group all aspect tokens into a single inference batch to leverage Triton's GPU scheduling.                                                                       
                                                                                                                                                                                    
  ### 5. BERTopic (Topic Modeling)                                                                                                                                                  
                                                                                                                                                                                    
  1. Selection Rationale: BERTopic is modular and builds coherent topic distributions. It uses MiniLM embeddings, UMAP for dimensionality reduction, and HDBSCAN for clustering,    
  resulting in robust topic generation.                                                                                                                                             
  2. Input Data: 384-dimensional review embeddings.                                                                                                                                 
  3. Output Data: Topic assignment ID, topic name label, and representative keywords.                                                                                               
  4. Training Strategy: Unsupervised transductive learning. Fit UMAP and HDBSCAN models on a large corpus of reviews to define the clusters, then compute class-based TF-IDF (c-TF- 
  IDF) weights for keywords.                                                                                                                                                        
  5. Fine-tuning Requirements: Tune hyperparameters for UMAP ( n_neighbors ,  n_components ) and HDBSCAN ( min_cluster_size ,  min_samples ) using grid search to find stable       
  cluster metrics.                                                                                                                                                                  
  6. Inference Workflow: Input Embedding → Project via UMAP → Map to cluster index via HDBSCAN → Output Topic details.                                                              
  7. Expected Latency: <5ms per review for projection and assignment.                                                                                                               
  8. Hardware Requirements: Multi-core CPU is sufficient.                                                                                                                           
  9. Storage Requirements: <25 MB for the serialized UMAP/HDBSCAN models and c-TF-IDF dictionaries.                                                                                 
  10. Scalability: Process topic updates in batch tasks (e.g., weekly cron jobs) to recalculate clusters on new reviews.                                                            
                                                                                                                                                                                    
  ### 6. BART (Summarization)                                                                                                                                                       
                                                                                                                                                                                    
  1. Selection Rationale: BART uses a bidirectional encoder and an autoregressive decoder. It is highly effective at multi-document summarization, condensing multiple review texts 
  into a coherent summary.                                                                                                                                                          
  2. Input Data: Concatenated review texts of a specific group (e.g., negative reviews for a product) up to 1024 tokens.                                                            
  3. Output Data: An executive summary paragraph (50 to 150 words).                                                                                                                 
  4. Training Strategy: Supervised Seq2Seq training. Start with  facebook/bart-large-cnn  and fine-tune on custom multi-review summaries.                                           
  5. Fine-tuning Requirements: Set up cross-entropy seq2seq loss using a learning rate of 3e-5, cosine warmup scheduling, and FP16 mixed precision.                                 
  6. Inference Workflow: Select grouped reviews → Format with separator tags → Tokenize → Auto-regressive generation (beam search) → Decode text.                                   
  7. Expected Latency: ~300ms to 600ms per group depending on generation length and beam size.                                                                                      
  8. Hardware Requirements: Dedicated GPU (NVIDIA A10G or L4).                                                                                                                      
                                                                                                                                                                                    
  • Storage Requirements: ~1.6 GB for weights.                                                                                                                                      
                                                                                                                                                                                    
  10. Scalability: Offload summarization to asynchronous background queues to prevent blocking API responses.                                                                       
                                                                                                                                                                                    
  ### 7. XGBoost (Helpfulness Prediction)                                                                                                                                           
                                                                                                                                                                                    
  1. Selection Rationale: XGBoost is highly efficient for tabular prediction tasks. It models non-linear interactions between readability, sentiment, and length features better    
  than standard neural nets, and inferences in sub-milliseconds.                                                                                                                    
  2. Input Data: Formatted tabular feature vector.                                                                                                                                  
  3. Output Data: Continuous predicted helpfulness score [0.0,1.0].                                                                                                                 
  4. Training Strategy: Supervised regression using Mean Squared Error (MSE) or Huber Loss.                                                                                         
  5. Fine-tuning Requirements: Grid search or Bayesian Optimization (Optuna) targeting hyperparameters ( max_depth ,  learning_rate ,  subsample ).                                 
  6. Inference Workflow: Load tabular vector → Forward pass through trees → Output float prediction.                                                                                
  7. Expected Latency: <1ms.                                                                                                                                                        
  8. Hardware Requirements: Standard CPU container.                                                                                                                                 
  9. Storage Requirements: <5 MB.                                                                                                                                                   
  10. Scalability: Highly scalable; handles millions of records per second on a single CPU core.

  ## 5. MLOps, Risks, and Optimization Blueprints                                                                                                                                   
                                                                                                                                                                                    
  ### MLOps Reference Design                                                                                                                                                        
                                                                                                                                                                                    
  • Version Control (DVC): Track training data splits and serialized weights. Keep large weights out of Git.                                                                        
  • Model Registry (MLflow): Register final trained models ( topic_model.pkl ,  helpfulness_model.pkl , and transformer checkpoints) to version model weights.                      
  • Observability & Drift (Prometheus & Grafana): Monitor prediction confidence scores, text lengths, and rating distributions. Alert developers if the Population Stability Index  
  (PSI) drifts past 0.2, which indicates text styles have shifted.                                                                                                                  
                                                                                                                                                                                    
  ### Risks & Optimization Guidelines                                                                                                                                               
                                                                                                                                                                                    
  • Transformer Cascades Latency: Processing reviews sequentially can take over 200ms.                                                                                              
      • Optimization: Compile models using TensorRT or ONNX Runtime for 3x speedups. Run independent models (RoBERTa, Sentence-Transformers, and spaCy) in parallel inside Celery   
      workers, rather than sequentially.                                                                                                                                            
  • Vector Search Performance: Running exact cosine similarity on millions of rows gets slow.                                                                                       
      • Optimization: Use pgvector's HNSW (Hierarchical Navigable Small World) index with  m=16  and  ef_construction=64 .                                                          
  • Memory Footprint: Loading BART (1.6GB), spaCy-TRF (400MB), DeBERTa (800MB), and RoBERTa (500MB) can cause Out-Of-Memory (OOM) failures.                                         
      • Optimization: Host the models on Triton Inference Server with dynamic batching. Triton manages memory allocation and queues request inputs dynamically.
